# System Design

## 1. Назначение

Документ фиксирует архитектуру PoC-системы, которая преобразует научную статью в трассируемый репликационный пакет: структурированное представление статьи, граф знаний, план реализации, черновые кодовые артефакты и журнал проверок. Архитектура рассчитана на управляемое поведение при неполной спецификации входа, частичных отказах инструментов и недоступности LLM API.

## 2. Архитектурные требования

### 2.1 Функциональные

Система должна:

- извлекать сущности, отношения, этапы метода и экспериментальные условия из статьи;
- записывать нормализованные факты во внешний граф знаний;
- использовать граф знаний как общее состояние координации агентов;
- строить план репликации и генерировать scaffold/черновые модули;
- выполнять проверки согласованности между источниками, графом, планом и артефактами;
- явно фиксировать assumptions, unresolved items и conflicts.

### 2.2 Нефункциональные

Приоритеты PoC:

1. стабильность выполнения;
2. надёжность результата и трассируемость;
3. ограничение стоимости и времени прогона;
4. безопасное поведение при ошибках;
5. воспроизводимость.

## 3. Ключевые архитектурные решения

### ADR-01. Оркестрация через явную state machine

Управление пайплайном реализуется не как свободный агентный цикл, а как конечный автомат с ограниченным числом состояний:

`INGEST -> EXTRACT -> NORMALIZE -> PLAN -> GENERATE -> VERIFY -> PACKAGE -> COMPLETE`

Дополнительные состояния:

`DEGRADED`, `WAIT_RETRY`, `PARTIAL_COMPLETE`, `FAILED`.

Следствие:

- уменьшается риск зацикливания;
- каждая стадия имеет формальный контракт входа/выхода;
- retry и fallback становятся детерминированными.

### ADR-02. Внешний граф знаний как единственный долговременный источник состояния

Долговременное состояние не хранится в prompt-цепочке. Каноническое состояние прогона находится во внешнем storage:

- graph store для сущностей и связей;
- document store для артефактов и ревизий;
- run store для статусов, бюджетов, ошибок и чекпоинтов.

Следствие:

- восстановление после сбоя возможно с последнего подтверждённого checkpoint;
- несколько модулей работают поверх единого версионированного состояния;
- любые спорные обновления можно откатить.

### ADR-03. LLM API изолируется через provider adapter

Оркестратор не вызывает LLM напрямую. Все обращения идут через слой `LLM Gateway` с единым контрактом:

- выбор primary/secondary provider;
- rate limiting;
- retry policy;
- circuit breaker;
- response validation;
- cost accounting.

Следствие:

- отказ одного провайдера не приводит к немедленному падению всего прогона;
- телеметрия по моделям и провайдерам унифицирована;
- упрощается миграция между моделями.

### ADR-04. Критические результаты проходят схему и source-grounding

Каждый критический выход агента должен быть:

- сериализован в структурированный формат;
- провалидирован схемой;
- привязан к источникам, если это факт из статьи;
- помечен как assumption, если источник отсутствует.

Следствие:

- снижается риск «тихой» галлюцинации;
- verification получает формальные входы.

### ADR-05. Fail-safe предпочтительнее ложной полноты

При нехватке данных система не достраивает вывод неявно. Разрешённый результат при сбое или неопределённости — частичный пакет с причинами остановки.

### ADR-06. Асинхронное исполнение с очередями между тяжёлыми стадиями

Стадии `EXTRACT`, `GENERATE`, `VERIFY` оформляются как независимые worker-задачи, связанные через очередь и идемпотентные команды.

Следствие:

- система выдерживает временную недоступность отдельных зависимостей;
- появляется backpressure-контроль;
- повышается утилизация ресурсов.

## 4. Состав модулей и роли

### 4.1 API / Frontend Layer

Назначение:

- приём статьи и параметров прогона;
- валидация запроса;
- выдача статуса и итогового пакета.

Не содержит бизнес-логики; только маршрутизация, аутентификация, лимиты и status API.

### 4.2 Orchestrator

Назначение:

- запуск state machine;
- управление шагами, retry, fallback и budget caps;
- фиксация checkpoint;
- перевод прогона в `DEGRADED` или `PARTIAL_COMPLETE`.

### 4.3 Ingestion Layer

Назначение:

- парсинг статьи;
- нормализация секций, ссылок, таблиц, формул и приложений;
- расчёт чанков для retrieval.

Выход:

- `DocumentManifest`;
- `SectionIndex`;
- `ChunkSet`;
- checksum входа.

### 4.4 Retriever

Назначение:

- индексирование чанков;
- гибридный поиск по секциям, семантике и метаданным;
- reranking;
- сбор evidence-пакета для агентов.

### 4.5 Extraction Agent

Назначение:

- выделение сущностей, отношений, этапов метода, данных, метрик, гиперпараметров;
- формирование кандидатов на факты с source spans.

### 4.6 Knowledge Graph / Memory Layer

Назначение:

- хранение сущностей, связей, версий, unresolved items, assumptions, conflicts;
- поддержка ревизий и rollback.

### 4.7 Planner

Назначение:

- построение плана реализации на основе графа знаний;
- декомпозиция на подзадачи;
- определение зависимостей между будущими кодовыми артефактами.

### 4.8 Code Generation Agent

Назначение:

- создание scaffold;
- генерация конфигураций и черновых модулей;
- выпуск README/notes по реализации.

### 4.9 Verification Agent

Назначение:

- consistency-check между графом, планом и кодом;
- schema validation;
- basic smoke/syntax checks;
- фиксация конфликтов.

### 4.10 Observability Layer

Назначение:

- метрики, логи, трейсинг;
- health-сигналы;
- алерты;
- аналитика деградаций и затрат.

## 5. Execution flow

### 5.1 Нормальный путь

1. Пользователь создаёт run.
2. API сохраняет вход и создаёт `run_id`.
3. Orchestrator запускает `INGEST`.
4. Ingestion строит нормализованный корпус и индексы.
5. Retriever подготавливает evidence-пакеты.
6. Extraction agent извлекает факты.
7. Normalizer валидирует и записывает факты в граф знаний.
8. Planner строит реализационный план.
9. Code generation agent выпускает scaffold и модули.
10. Verification agent выполняет проверки.
11. Packaging layer формирует итоговый пакет.
12. Run переводится в `COMPLETE` или `PARTIAL_COMPLETE`.

### 5.2 Деградированный путь при отказе LLM API

1. Gateway получает timeout/5xx/rate-limit.
2. Срабатывает policy retry с bounded backoff.
3. После достижения порога ошибок открывается circuit breaker.
4. Оркестратор пытается перевести вызов на secondary model/provider.
5. Если fallback невозможен, шаг помечается `DEGRADED`.
6. Если стадия некритична, pipeline продолжает выполнение в ограниченном режиме.
7. Если стадия критична, run завершается как `PARTIAL_COMPLETE` с журналом причин.

### 5.3 Деградированный путь при конфликте данных

1. Verification обнаруживает противоречие между источниками или артефактами.
2. Конфликт записывается в граф как `ConflictRecord`.
3. Автоматическое продвижение в code generation запрещается для конфликтующих узлов.
4. Итоговый пакет содержит конфликт и источник его происхождения.

## 7. State / memory / context handling

### 7.1 Уровни состояния

#### Эфемерное состояние шага

Существует только во время одного вызова worker:

- raw prompt payload;
- временные кандидаты на факты;
- промежуточные логи выполнения.

После завершения шага сохраняются только проверенные результаты.

#### Сессионное состояние прогона

Хранится до завершения run:

- stage status;
- budget usage;
- retry counters;
- selected model/provider;
- pointers на артефакты.

#### Долговременная память

Хранится независимо от run:

- граф знаний;
- ревизии артефактов;
- агрегированная телеметрия;
- evaluation results.

### 7.2 Context budget policy

Контекст LLM не заполняется всем корпусом. Используется policy:

1. system instructions;
2. task schema;
3. top-k retrieval evidence;
4. краткое состояние текущего этапа;
5. только необходимые unresolved items.

Ограничения:

- фиксированный upper bound на токены запроса;
- дедупликация пересекающихся чанков;
- summarization только для некритического контекста;
- source spans никогда не суммаризируются так, чтобы терялась трассируемость.

### 7.3 Checkpoint policy

Checkpoint записывается после завершения стадий:

- `INGEST`
- `EXTRACT`
- `NORMALIZE`
- `PLAN`
- `GENERATE`
- `VERIFY`

Восстановление всегда идёт с последнего подтверждённого checkpoint. Повторный запуск шага обязан быть идемпотентным.

## 8. Retrieval-контур

### 8.1 Источники

Для PoC источниками считаются:

- основной текст статьи;
- приложения;
- подписи таблиц и рисунков;
- связанные текстовые артефакты, явно переданные пользователем.

### 8.2 Пайплайн retrieval

1. Чанкование с сохранением section-aware метаданных.
2. Построение sparse-индекса и dense-индекса.
3. Гибридный поиск по запросу агента.
4. Reranking кандидатов.
5. Сбор evidence-pack со ссылками на источники.

### 8.3 Требования к надёжности retrieval

- retrieval не должен возвращать фрагменты без provenance;
- при пустом результате агент получает пустой evidence-pack, а не синтетическое заполнение;
- индексирование должно быть повторяемым для одинакового входа;
- ошибки индексации не должны повреждать ранее подтверждённую ревизию индекса.

## 9. Tool/API-интеграции

### 9.1 LLM Gateway

Контракт:

- `task_type`
- `schema_id`
- `timeout_ms`
- `max_retries`
- `fallback_policy`
- `budget_class`

Защитные механизмы:

- per-provider timeout;
- exponential backoff с jitter;
- circuit breaker;
- provider health score;
- ограничение параллелизма по модели;
- schema validation на выходе;
- отказ от принятия partially parsed response как валидного результата.

### 9.2 Graph Store Adapter

Контракт:

- versioned upsert;
- optimistic concurrency control;
- read by revision;
- rollback.

### 9.3 Code Execution Sandbox

Контракт:

- ограниченный CPU/memory/time;
- запрет внешней сети по умолчанию;
- ограниченный временный filesystem;
- детерминированный capture stdout/stderr.

## 10. Failure modes, fallback и guardrails

### 10.1 Классы отказов

#### A. Отказы внешних API

Примеры:

- timeout;
- 429/rate limit;
- 5xx;
- provider outage;
- malformed response.

Реакция:

- bounded retry;
- переключение на backup provider/model;
- снижение размера батча/контекста;
- частичный результат вместо бесконечного повтора.

#### B. Отказы данных

Примеры:

- пустой или плохо распарсенный текст;
- конфликтующие сведения;
- отсутствующие секции;
- неоднозначные гиперпараметры.

Реакция:

- unresolved item;
- conflict record;
- блокировка перехода в следующий критический этап без пометки.

#### C. Отказы внутренней инфраструктуры

Примеры:

- падение worker;
- повреждённый checkpoint;
- отказ graph store;
- переполнение очереди.

Реакция:

- restart с checkpoint;
- dead-letter queue;
- backpressure;
- readonly/degraded режим при временной недоступности non-critical компонента.

### 10.2 Guardrails

- строгие JSON/schema-контракты для критических ответов;
- запрет исполнения кода вне sandbox;
- allowlist инструментов;
- budget caps по токенам, времени, числу шагов и стоимости;
- policy-check перед каждым action с side effect;
- mandatory source grounding для критических фактов;
- stop condition после исчерпания лимита retry.

## 11. Observability и контроль стабильности

### 11.1 Метрики уровня системы

- run success rate;
- partial completion rate;
- stage success rate;
- p50/p95/p99 latency по стадиям;
- end-to-end latency;
- error rate по типам;
- queue depth;
- worker saturation;
- token usage и cost/run.

### 11.2 Метрики LLM Gateway

- success rate по provider/model;
- timeout rate;
- schema validation failure rate;
- fallback activation rate;
- circuit breaker open duration;
- tokens/request;
- cost/request.

### 11.3 Метрики качества и надёжности результата

- доля fact records с source grounding;
- число unresolved items на run;
- число conflict records на run;
- consistency pass rate;
- syntax/smoke pass rate для артефактов.

### 11.4 Алерты

Критические алерты:

- рост 5xx/timeout по primary provider выше порога;
- длительно открытый circuit breaker;
- stage failure rate выше порога;
- рост partial completion rate;
- queue lag выше SLA;
- исчерпание бюджета на run до завершения.

## 12. Надёжность при недоступности LLM API

### 12.1 Fallback matrix

| Условие | Действие | Предел |
|---|---|---|
| 1–2 transient timeout | retry на том же provider | до `N1` попыток |
| 429/rate limit | backoff + снижение параллелизма | до `N2` секунд ожидания |
| серия 5xx | открыть circuit breaker | cooldown `T1` |
| provider unavailable | переключение на secondary provider | 1 переключение на стадию |
| secondary тоже недоступен | перевод шага в `DEGRADED` | без повторного цикла |
| стадия критична и нет валидного результата | `PARTIAL_COMPLETE` | немедленно |

### 12.2 Правила деградации

- verification и packaging могут продолжаться на уже имеющихся артефактах;
- code generation не запускается для plan items без подтверждённых фактов;
- extraction может использовать меньшие батчи и более дешёвую модель для non-critical normalization;
- при системной деградации отключаются дорогие дополнительные проверки, но не обязательные safety-check.

### 12.3 Что запрещено

- бесконечный retry;
- повтор без учёта идемпотентности;
- скрытая замена отсутствующего ответа догадкой;
- silent success при провале schema validation.

## 13. Утилизация и оптимальность использования ресурсов

### 13.1 Контроль стоимости

- budget class назначается на каждый шаг;
- оркестратор ведёт cumulative token/cost budget;
- при достижении soft limit активируются cheaper fallbacks;
- при достижении hard limit run останавливается с частичным результатом.

### 13.2 Контроль CPU/RAM/очередей

- тяжёлые стадии выполняются в отдельных worker pools;
- concurrency ограничивается по классу нагрузки;
- queue length регулирует admission control;
- sandbox jobs получают жёсткие memory/time limits.

### 13.3 Оптимизация LLM-потребления

- reuse retrieval evidence между соседними шагами;
- кеширование детерминированных промежуточных результатов;
- дедупликация почти одинаковых запросов;
- batch extraction только для независимых секций;
- запрет повторной генерации валидного артефакта без изменения входной ревизии.

## 14. Точки контроля

Контрольные точки, через которые запрещено проходить без явного статуса:

1. после ingestion — подтверждение корректности корпуса;
2. после extraction — валидация схемы фактов;
3. после записи в KG — фиксация ревизии;
4. перед planning — проверка минимальной полноты фактов;
5. перед generation — отсутствие unresolved/conflict для критических plan items;
6. после generation — syntax/smoke check;
7. перед final package — consistency summary и error summary.

## 15. Технические и операционные ограничения

### 15.1 Ограничения PoC

- без обязательного запуска тяжёлых вычислительных экспериментов;
- без автономной установки внешних зависимостей вне sandbox;
- без автоматической публикации артефактов во внешние сервисы;
- без неограниченного agent loop.

### 15.2 Операционные лимиты

- upper bound на число агентных шагов на run;
- upper bound на число retries по каждому внешнему API;
- upper bound на токены и стоимость на run;
- SLA на время удержания очереди;
- retention policy для логов и артефактов.
